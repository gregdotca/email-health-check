Sending tests

Can I test from a Gmail, Outlook.com or other personal address?

Yes, but the report is then about that provider's domain (gmail.com, for example), not yours. To check your own domain, send from an address at your domain, through the system that normally sends its mail.

I sent from an alias or a "send as" address. Why didn't the report come?

The report goes to the From: address, and only when the envelope sender (Return-Path) is at the same domain. Some mail systems send an alias's mail with an envelope sender at another domain, so no report is emailed. The report is still kept online: look it up with either address.

Does the report go to my Reply-To address?

No. The Reply-To header is ignored: the report always goes to the From: address.

Can I forward a message to the test address?

Using Forward in your mail program creates a new message from you, so the report is about your address and how your mail is sent, not about the original message.

Automatic forwarding (a rule that redirects mail) passes the original message on through another server. SPF and PTR are then checked for that server instead of the original sender's (SPF usually fails), and forwarding can break DKIM. To test your own mail, send a new message straight to {{ m.address(v) }}.

How do I test a subdomain, such as news.example.com?

Send from an address at the subdomain: the report is about the domain in the From: address. Two things to expect:

  • "Can receive email" checks the subdomain's own MX records. A subdomain that only sends mail often has none, so it shows {{ false|mark }}. If the subdomain should receive replies or bounces, give it MX records.
  • If the subdomain has no DMARC record of its own, the one for its main domain applies, including its sp= policy (see DMARC).

We use several mail services. Which one does a test check?

Only the one that sent the test. Your mailboxes, a newsletter service and a ticket system each send from their own servers and need their own SPF and DKIM set-up, so test each one separately.

My test landed in the test address's spam folder. Does that matter?

No. The spam folder is checked too (see which folders), and the folder never affects the results: "Can send email" only means the test arrived.

Keep in mind that SPF, DKIM and DMARC show whether your mail is authenticated, not whether it lands in the inbox: every receiver also applies its own spam, reputation and content checks.

Can a test be refused before it's checked?

Yes. The receiving mail server runs its own spam and policy checks first. A message it rejects or deletes, for example one that looks very like spam or that fails a strict DMARC policy (p=reject), never reaches the check, so there's no report at all. Look for a bounce message in your mailbox, which usually gives the reason.

Can I send several tests in a row?

Yes, within the limits. Each gets its own report email, and each email's link opens that particular report. Looking up the address shows the newest one, and showing any report deletes the older ones from the same address, so links in earlier report emails then stop working.

I fixed my DNS, but the new test says the same thing.

DNS answers are cached for as long as the record's TTL (time to live) says, often an hour or more, so a change can take that long to be seen everywhere, including by the check. Wait for the old record's TTL to pass, then send another test.

Understanding the results

Why does SPF pass but DMARC fail?

SPF checks the envelope sender's domain, which a mail service often sets to its own. SPF can then pass for the service's domain without matching your From: domain, so it doesn't count for DMARC. Setting up DKIM for your domain with the service usually fixes it (see Alignment).

The report shows a DKIM signature from a domain I don't recognise.

It's usually your mail provider's own signature, which many providers add to everything they send. That's fine alongside your own, but it doesn't replace it: you still need a signature for your domain (any domain under it, such as mail.example.com, counts). An extra signature that fails is still flagged, even when yours passes.

The report says the message needs exactly one From: address.

The test had no From: address, or more than one. DMARC can't be checked, and no report is emailed. Send a normal message from a single address.

Why does a value end in "…"?

Very long values, such as a huge subject or record, are cut off to keep reports a sensible size. Encoded subjects (common from marketing services) are shown decoded, as you'd read them.

Does it work with IPv6?

Yes. If your server delivered the test over IPv6, SPF and PTR are checked for its IPv6 address, so your SPF record has to cover it (with ip6:, a provider's include, or a or mx that resolve to it), and the address needs reverse DNS too.

Reports online

Can I share a report?

Forward the report email, or share its summary picture. Anyone with the link at the end of the email can see the report online while it's kept, but the first view starts its {{ v.viewed_minutes }}-minute clock for everyone.

Several of us test from the same address.

Looking up the address shows everyone the same, newest report, and showing it deletes the older ones. Use the link in your own report email instead, or look up soon after your test. The emailed reports aren't affected.

Which address do I look up?

The From: address the test was sent from. The envelope sender (Return-Path) works too, but some services use one envelope sender for many customers, so looking that up can show someone else's newer test. Capital letters don't matter.

Running your own

Does it work with mail servers other than Exim?

Not without changes. It reads the receiving server's Received: header in Exim's format (see What's trusted). Other formats are rejected or only partly understood: for example, the sending IP may be found but not the envelope sender, so SPF checks the wrong name and no report is emailed. Adapt healthcheck/received.py first.

I changed .env. Why didn't anything change?

Settings are read when the services start. Run docker compose up -d after changing .env: Compose recreates the services whose settings changed.

Can two copies use the same mailbox?

Avoid it. Tests are split unpredictably between the copies, and both can pick up the same message before either deletes it, so it's answered twice. A copy with DRY_RUN=True next to a live one only sees the messages it happens to reach before the live copy deletes them.

What should I know about DRY_RUN?

Nothing is sent, flagged or deleted, so test messages pile up in the mailbox. Each message is only handled once while the poller runs, but after a restart every message still in the mailbox is checked again.

What happens to a report waiting to be retried if the poller restarts?

The retry schedule is kept in memory, so the message, still in the mailbox, is handled again from the start: checked again, and its report sent (and counted against the limits) as if new.

The lookup limit blocks everyone at once, or doesn't seem to apply.

TRUSTED_PROXY_HOPS doesn't match the number of reverse proxies in front of the website. Too low, and every visitor looks like the proxy, so they share one limit. Too high, and visitors can pretend to be someone else with a made-up X-Forwarded-For header. Set it to the number of proxies that add that header, and 0 if the website is reached directly.

Can the website live under a path, such as example.com/health-check/?

No. PUBLIC_URL must be a site of its own, like https://check.example.com, because the report links and these docs are at fixed paths from its root.

How do I report a security problem?

Privately, as described in SECURITY.md in the project's repository, not in a public issue.
