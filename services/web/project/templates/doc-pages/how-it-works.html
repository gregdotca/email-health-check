{{ app_title }} is open source. This section is for anyone running their own copy. You don't need it to use this one.

Two services

One Docker image runs as two services, which share a small SQLite database:

poller
Checks the test mailbox over IMAP every POLL_SECONDS, checks each message, saves the report for the website, emails the report back over SMTP, then deletes the message. It always runs. It handles up to {{ v.max_per_poll }} messages per check, taking turns between folders so a busy inbox can't hold up the others.
web
Optional: this website, a small Flask app served by gunicorn behind your own reverse proxy. It shows reports looked up by address or by the link in the email, and these docs. Without it, reports are only emailed and nothing is kept.

The poller reads the inbox and any folder the mail server marks as junk, or named exactly Junk, Spam, INBOX.Junk, INBOX.Spam, Junk E-mail, Junk Email or Bulk Mail (any capitalization). Other folders aren't read, so make sure no mailbox rule moves tests elsewhere. The folder list is refreshed hourly.

The database holds only short-lived reports and rate-limit counters, which expire on their own: the poller clears out expired ones at least once a minute, even while the mail server can't be reached.

What happens to a test

  1. The poller finds the message in the mailbox and downloads it (messages over {{ v.max_mb }} MB are deleted without being downloaded, and one whose size the server doesn't report waits for the next check).
  2. It finds the receiving mail server's Received: header and takes the sending server's IP address, its HELO name and the envelope sender from it.
  3. It runs the checks: PTR and MX lookups, SPF for the sending IP, DKIM for each signature (using the message's text, in memory only), then DMARC. SPF has 20 seconds, and the other DNS lookups share 30 seconds, so a domain whose DNS answers slowly can't hold up everyone else's tests.
  4. With the website, it saves the report (headers and results, never the text) under a random code.
  5. It decides whether to reply (see Who gets the report and the limits), and emails the report.
  6. If the message couldn't be checked at all, a short report saying so is kept online, and no email is sent.
  7. It deletes the message from the mailbox. If the email couldn't be sent for a temporary reason, the message is kept and sending is retried on later checks of the mailbox (at least {{ v.retry_schedule }} minutes apart, up to {{ v.max_attempts }} attempts) before it's deleted.

What's trusted

Every Received: header below the one your own receiving server wrote was added by the sender's side and could be forged, so the checks only trust the header written by a server named in TRUSTED_MX_HOSTS. A backup MX relaying to the main one is recognised by its verified reverse DNS, never by the name it gives in HELO.

Some receiving servers add their own authentication verdicts to the headers (such as Authentication-Results or spam scores). They can't be told apart from forged copies, so they're never used: every check is done from scratch.

The header parser is written for the format Exim uses (from <helo> ([<ip>]) by <server> with esmtp … (envelope-from <…>)). Other mail servers need changes to healthcheck/received.py.
